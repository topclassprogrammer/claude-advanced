# Research: загрузка и хранение файлов встречи

**План:** docs/plan-meeting-file-upload-and-storage.md
**PRD:** docs/prd-meeting-file-upload-and-storage.md
**Дата:** 2026-08-19

Цель документа — зафиксировать технологические решения для каждой фазы плана: какими средствами NestJS/Prisma/Next.js реализовать загрузку/скачивание/удаление файла встречи, почему выбран именно этот вариант и какие альтернативы были отклонены.

---

## 1. Backend: приём файла (multer)

### Решение: `@nestjs/platform-express` + встроенный `FileInterceptor` (multer), **diskStorage**, без стриминга в первой итерации

NestJS на Express-адаптере (уже используется в проекте, `main.ts` явно создаёт `ExpressAdapter`) из коробки тянет `multer` как peer-зависимость через `@nestjs/platform-express`, который уже установлен. Это самый маленький по объёму нового кода вариант — не нужно добавлять `multer` и `@types/multer` в `package.json` вручную (они разрешаются транзитивно; `@types/multer` стоит всё же добавить в `devDependencies` явно ради типа `Express.Multer.File`).

**Почему diskStorage, а не memoryStorage:**
- `memoryStorage` (дефолт `FileInterceptor` без опций) буферизует весь файл в RAM процесса Node — при лимите 100 МБ и нескольких параллельных загрузок это прямой риск OOM для dev/staging инстанса без масштабирования.
- `multer.diskStorage({ destination, filename })` пишет файл на диск потоково по мере получения chunk'ов от клиента, до срабатывания бизнес-валидации в handler'е. Это соответствует пункту плана «настроить каталог хранения файлов на диске».

**Почему не потоковая запись «мимо multer» (raw `req` pipe в handler):**
Технически более экономный по памяти вариант — читать `multipart/form-data` вручную (`busboy`/`@fastify/multipart`-подобный подход) и валидировать MIME по magic bytes до полной записи на диск, прерывая поток при превышении лимита. Для MVP это избыточная сложность: `multer` уже даёт лимиты (`limits: { fileSize }`) на уровне Busboy (multer использует busboy под капотом), которые прерывают приём потока при превышении, не считывая файл целиком в память — то есть даже с `diskStorage` контроль размера не требует пост-фактум проверки уже сохранённого файла. Ручной busboy стоит рассматривать только если позже понадобится, например, вычисление контрольной суммы на лету или antivirus-сканирование потока.

### Валидация MIME-типа и размера

- **Размер** — `FileInterceptor('file', { limits: { fileSize: 100 * 1024 * 1024 } })`. При превышении multer прерывает upload и Express получает ошибку `LIMIT_FILE_SIZE`; Nest транслирует её в 413, но по умолчанию тело ошибки multer невнятное — стоит завести `Filter` (`MulterExceptionFilter` или обработку в самом controller через `try/catch` вокруг `FilesInterceptor`) либо кастомный `exceptionFactory`, чтобы вернуть предсказуемый JSON (`400`/`413` с понятным `message`), который фронтенд Фазы 4 сможет показать пользователю.
- **MIME-тип** — **нельзя доверять `file.mimetype` от multer**: это значение приходит из заголовка `Content-Type` самого multipart-part, который полностью контролируется клиентом и подделывается тривиально (curl, поменянный заголовок в браузере через DevTools). Для реальной проверки содержимого нужна библиотека, читающая magic bytes — **`file-type`** (пакет `file-type`, ESM-only начиная с v17+, либо форк `file-type-cjs` для CommonJS-проекта — учитывая, что `apps/api` целиком на CommonJS (`moduleFormat: "cjs"` в Prisma и обычный `tsconfig` без `"module": "nodenext"`/ESM), проще использовать динамический `await import('file-type')` внутри async-хендлера, что в CJS с Node 18+/20+ работает без проблем, либо `file-type-cjs`). Проверка выполняется в handler'е **после** сохранения multer'ом временного файла на диск: читаем первые байты, определяем реальный MIME, сверяем со списком допустимых — если не совпадает, удаляем файл и кидаем `BadRequestException`.
  - Компромисс для MVP, соответствующий плану («список допустимых MIME-типов»): можно ограничиться проверкой заявленного `mimetype`/расширения для скорости реализации Фазы 1, но явно задокументировать это как известный gap безопасности (spoofing MIME) и включить magic-byte-проверку через `file-type` не позднее Фазы 2 («метаданные, удаление, авторизация»), где и так расширяется валидация. Рекомендация этого research — **сразу заложить `file-type`-проверку в Фазу 1**, так как её отсутствие — это возможность загрузить, например, исполняемый файл под видом `image/png` и раздать его на скачивание другим участникам встречи (все они получают `Content-Type` из БД, а не из реального содержимого).

### Куда и как класть файл на диск

- Каталог `apps/api/storage/meeting-files/` (или `apps/api/uploads/`), путь берётся из `ConfigService` (`STORAGE_DIR`, дефолт относительно `process.cwd()`), добавляется в `apps/api/.gitignore` (по аналогии с `/generated/prisma`) и создаётся при старте приложения (`fs.mkdirSync(dir, { recursive: true })` в `main.ts` или в конструкторе сервиса хранения).
- **Имя файла на диске ≠ оригинальное имя файла.** Оригинальное `filename` пользователя хранится только в колонке БД `MeetingFile.filename`; физическое имя на диске — `<meetingId>` или `${meetingId}-${randomUUID()}${ext}`, генерируется в `multer.diskStorage({ filename: (req, file, cb) => ... })`. Причины: (1) traversal-атаки через `../` в оригинальном имени, (2) коллизии одинаковых имён от разных встреч, (3) поле `MeetingFile.meetingId` в плане — уникальная связь 1:1 с `Meeting`, так что вариант «имя файла на диске = meetingId» одновременно упрощает поиск файла при скачивании/удалении (не нужно хранить `storagePath` отдельно, если использовать предсказуемый путь) — но план явно указывает поле `storagePath` в модели, поэтому лучше не завязываться на конвенцию имени и просто сохранять фактический путь, который вернул multer, в `storagePath`. Это также даёт свободу при будущей миграции на объектное хранилище (см. §4) — `storagePath` в разных бэкендах означает разное (relative path на диске vs. object key в S3), и абстракция об этом не должна знать.
- Расширение файла на диске стоит сохранять (`path.extname(file.originalname)`) — упрощает ручную отладку и совместимо с некоторыми антивирус/preview-инструментами, которые смотрят на расширение.

### Абстракция хранения (важно для будущей замены на S3/облако)

Даже не реализуя сразу S3, стоит с Фазы 1 выделить небольшой интерфейс `FileStorageService` (или provider с токеном `FILE_STORAGE`) с методами `save(buffer|stream, meta): Promise<{ storagePath, size }>`, `read(storagePath): ReadStream`, `delete(storagePath): Promise<void>`, и один реализующий его класс `LocalDiskStorageService`. Это не добавляет заметной сложности к плану (все методы — тонкие обёртки над `fs`), но избавляет от необходимости менять сигнатуры хендлеров команд/запросов, если позже понадобится `S3StorageService` — поменяется только DI-биндинг в модуле. Здесь `multer.diskStorage` всё равно используется на уровне интерсептора (Nest/Express так спроектированы — тело файла должно быть считано интерсептором до входа в handler), но **перемещение** временного файла multer'а в финальное расположение стораджа и **удаление** делегируются этому сервису, а не разбросаны по хендлерам.

## 2. Backend: схема данных (Prisma)

Модель по плану:

```prisma
model MeetingFile {
  id          String   @id @default(uuid())
  meetingId   String   @unique
  meeting     Meeting  @relation(fields: [meetingId], references: [id], onDelete: Cascade)
  filename    String
  size        Int
  mimeType    String
  storagePath String
  uploadedAt  DateTime @default(now())
}
```

Заметки:
- **`meetingId @unique`** реализует связь 1:1 (Prisma моделирует one-to-one через unique FK на стороне, где хранится ссылка) — план явно требует «meetingId — уникальная связь 1:1 с Meeting», это стандартный Prisma-паттерн, дополнительных решений не требует.
- **`onDelete: Cascade`** на связи `meeting` — по аналогии с существующим `Meeting.organizerId → User` (тоже `Cascade`), чтобы удаление встречи не оставляло висящую запись `MeetingFile` и не ломало очистку таблиц в e2e-тестах (паттерн уже задокументирован в `apps/api/CLAUDE.md`).
- **`size Int`** — план указывает `Int`; при лимите 100 МБ (104 857 600 байт) это укладывается в диапазон `Int32` (макс. ~2.1 млрд) с большим запасом, дополнительных типов (`BigInt`) не требуется, но если лимит когда-либо вырастет за ~2 ГБ, тип придётся менять — стоит просто иметь это в виду, не блокер для текущего плана.
- Обратная сторона связи (`Meeting.file MeetingFile?`) в модели `Meeting` добавляется автоматически Prisma при генерации (или явно дописывается в `Meeting` для симметрии — по существующему стилю схемы, где `User.meetings Meeting[]` объявлено явно, стоит явно дописать и `Meeting.file MeetingFile?`).
- Миграция создаётся штатно: `npm run prisma:migrate:dev --workspace=api` (или из `apps/api`), затем `npm run prisma:generate --workspace=api` — как описано в `apps/api/CLAUDE.md`. Обращаться к `prisma-cli`/`prisma-client-api` skills при формулировке миграции/запросов (доступны в проекте под `apps/api/.claude/skills`).

## 3. Backend: отдача файла на скачивание

### Решение: `StreamableFile` (встроенный класс Nest) поверх `fs.createReadStream`, не `res.sendFile`/`res.download` напрямую

Nest с версии 8+ имеет `StreamableFile` — обёртку над Node `Readable`, которую можно вернуть из controller-метода, и Nest сам выставит `Content-Type`/стримит тело ответа, оставляя контроль над остальными заголовками (`Content-Disposition`, `Content-Length`) через `@Res({ passthrough: true })`. Это вписывается в CQRS-паттерн проекта: `GetMeetingFileQuery`/Handler достаёт метаданные (`storagePath`, `filename`, `mimeType`, `size`) из БД и проверяет права доступа (что встреча принадлежит текущему пользователю — по аналогии с `GetMeetingByIdHandler`, который уже ищет встречу вместе с `organizerId`), а controller открывает поток на диске и оборачивает в `StreamableFile`, устанавливая заголовки:

```ts
res.set({
  'Content-Type': meta.mimeType,
  'Content-Disposition': `attachment; filename="${encodeRFC5987(meta.filename)}"`,
});
return new StreamableFile(createReadStream(meta.storagePath));
```

**Почему не читать файл целиком в память и не отдавать `Buffer`:** при 100 МБ лимите буферизация всего файла в handler'е на каждое скачивание не масштабируется при параллельных запросах (та же проблема, что с `memoryStorage` при приёме). Стриминг с диска держит в памяти только текущий chunk.

**Про имя файла с не-ASCII символами (кириллица в `filename`):** `Content-Disposition: attachment; filename="..."` в чистом виде ломается на не-ASCII именах в части браузеров/HTTP-клиентов. Стандартный обходной путь — RFC 5987/6266 синтаксис с двумя параметрами одновременно:
```
Content-Disposition: attachment; filename="fallback.ext"; filename*=UTF-8''%D0%BE%D1%82%D1%87%D1%91%D1%82.pdf
```
где `filename` — ASCII-транслитерация/заглушка, `filename*` — `encodeURIComponent` реального имени. Учитывая, что PRD/план — русскоязычный проект, где пользователи почти наверняка будут называть файлы кириллицей («Протокол встречи.docx»), эту деталь стоит закрыть в Фазе 1/2, а не откладывать — иначе `meeting-file.e2e-spec.ts` может случайно не покрыть кириллицу и баг всплывёт только на визуальной проверке в Фазе 3.

### Авторизация на GET/DELETE

Согласовано с уже существующим паттерном `GetMeetingByIdHandler` (404, если встреча не найдена **или принадлежит другому пользователю** — не 403, чтобы не палить факт существования чужой встречи). Для `MeetingFile` план явно требует **403** при попытке удаления не-владельцем (в отличие от «404 при чужом просмотре» для самой встречи) — то есть здесь сознательно другая семантика: сначала проверяется, что встреча существует и текущий пользователь имеет к ней доступ (просмотр — доступен любому участнику встречи или только организатору? План не уточняет для GET/download, но для DELETE явно «только организатор» → 403 для остальных). Стоит явно решить на уровне реализации Фазы 2: имеют ли **участники** встречи (не только организатор) право скачивать/видеть файл, или доступ на чтение файла тоже ограничен организатором — сейчас `Meeting.participants` в схеме — это `String[]` (вероятно, email/имена, не `userId`), то есть техической связи участник → аккаунт нет, и по факту приложением сейчас может управлять только организатор (единственный, у кого есть `GET /meetings/:id` через `organizerId`-фильтр). Значит для файла естественно распространить то же ограничение: **чтение и скачивание — тоже только организатор**, а не «участник», раз участники не являются авторизованными пользователями системы в текущей модели данных. Это не решение, требующее нового технологического выбора — просто нужно явно защёлкнуть в PRD/реализации, чтобы не разъехались 401/403/404 семантики между эндпоинтами.

## 4. Хранилище файлов: локальный диск сейчас, что дальше

План прямо ограничивает Фазу 1 локальным диском («каталог хранения файлов на диске»). Ключевой технологический риск, который стоит явно назвать в этом research: **локальный диск не переживает горизонтальное масштабирование/эфемерные контейнеры** (Heroku, большинство serverless/PaaS с ephemeral filesystem, k8s без persistent volume) — если `apps/api` когда-либо будет задеплоен на такую платформу, файлы, загруженные на один под/dyno, будут недоступны с другого. Для текущего этапа проекта (нет ещё продакшен-деплоя, судя по структуре репозитория — только `docker-compose.yml` для локальной Postgres) это не блокер, но абстракция `FileStorageService` из §1 — это именно та точка, которая позволит позже подставить `S3StorageService` (AWS S3 / S3-совместимое типа Cloudflare R2/MinIO) без изменения контроллеров/хендлеров команд. Рекомендация: не реализовывать S3 сейчас (не входит в план, добавляет OAuth/ключи/инфраструктурную сложность непропорционально MVP), но не пропускать шаг с интерфейсом хранилища — цена абстракции здесь на уровне «один интерфейс + один класс», а не архитектурного разрастания.

## 5. Frontend: загрузка файла с прогресс-баром (Фаза 4)

### Решение: `XMLHttpRequest` напрямую (не `fetch`), обёрнутый в промис-хелпер внутри `meeting-file-api.ts`

Ключевое технологическое ограничение: **`fetch()` в браузере не поддерживает отслеживание прогресса загрузки исходящего тела запроса** (`upload progress`) — `fetch` даёт `ReadableStream` только для *скачивания* ответа (`response.body`), не для *отправки* запроса. Поддержка `ReadableStream` как `body` запроса существует в части браузеров, но событий прогресса всё равно нет без ручного оборачивания потока. Стандартный и до сих пор единственный нативный браузерный способ показать прогресс *загрузки* файла — это `XMLHttpRequest` с событием `xhr.upload.addEventListener('progress', (e) => e.loaded / e.total)`.

Раз проект уже использует тонкие fetch-обёртки (`src/lib/auth-api.ts`, `src/lib/meeting-api.ts`) и кидает единый `ApiError`, для `meeting-file-api.ts` стоит сохранить тот же контракт (`ApiError` с сообщением из ответа API), но конкретно для `uploadMeetingFile(meetingId, file, onProgress)` — реализовать через `XMLHttpRequest`, а для `getMeetingFile`/`deleteMeetingFile` — обычным `fetch`, как остальные методы. Это не架构ное расхождение, а точечное использование другого браузерного API там, где `fetch` объективно не даёт нужной возможности.

Альтернатива — сторонняя библиотека (`axios` с `onUploadProgress`) — не нужна: добавляет зависимость ради одной функции, которую `XMLHttpRequest` покрывает в ~20 строках, и ломает единообразие с остальными fetch-based клиентами проекта.

### Drag-and-drop зона

Нативные Drag and Drop API браузера (`ondragover`/`ondrop`, `event.dataTransfer.files`) — без сторонней библиотеки, реализация на уровне одного React-компонента с `useState` для `isDragging`/выбранного файла. Библиотека `react-dropzone` — популярный вариант, но для одного файла (не множественной загрузки, не сложных `accept`-паттернов) она добавляет зависимость ради малого выигрыша; проект пока не тянет сторонние UI-хелперы такого рода (только HeroUI + Tailwind). Рекомендация: **нативный DnD**, компонент `FileDropzone`/встроить в форму загрузки Фазы 4, с fallback `<input type="file">` (клик по зоне открывает системный файловый диалог) — так и требует план («drag-and-drop зона + выбор файла кликом»).

### Иконка типа файла по MIME

Небольшая чистая функция `getFileIcon(mimeType: string)`, маппящая префиксы (`image/*`, `application/pdf`, `application/vnd.openxmlformats-officedocument.*`, `video/*`, и т.д.) на набор SVG-иконок по аналогии с существующими `src/components/icons/*` (`EyeIcon.tsx`, `UsersIcon.tsx`) — не требует сторонней иконочной библиотеки для нескольких типов файлов, соответствует текущей конвенции проекта (собственные inline SVG-компоненты, а не icon-пакет).

### Валидация на клиенте до отправки

Проверка `file.size` и `file.type` в браузере **до** `XMLHttpRequest.send()` — даёт мгновенную обратную связь без траты трафика на заведомо отклоняемый файл, но **не заменяет** серверную валидацию (§1) — `file.type` в браузере тоже читается из расширения/MIME, который сообщает ОС, и может быть пустым/неточным для нестандартных типов; сервер обязан перепроверять. Список допустимых типов и лимит размера стоит вынести в общую константу (например, экспортировать из `meeting-file-api.ts` или отдельного `src/lib/meeting-file-constraints.ts`), чтобы подсказка в UI («допустимые типы и лимит 100 МБ» — пункт плана) не разъезжалась с реальными серверными ограничениями; в идеале эти константы должны буквально совпадать с списком на backend (нет общего пакета между `apps/web`/`apps/api` в текущей монорепо-структуре — совпадение поддерживается вручную/комментарием-ссылкой, заводить shared-package ради одной константы избыточно для этого масштаба проекта).

## 6. Frontend: e2e-инфраструктура (Playwright, Фаза 3)

План явно указывает: `apps/web` пока не имеет автоматического e2e-раннера (только ручная визуальная проверка через Playwright MCP), и Фаза 3 должна добавить `@playwright/test`.

Технические решения:
- **Пакет и конфиг:** `@playwright/test` как `devDependency` в `apps/web/package.json`, конфиг `playwright.config.ts` в корне `apps/web`. `webServer` в конфиге должен поднимать `next dev` (или `next build && next start` для более честного прогона, но `next dev` быстрее для локальной разработки/CI без лишнего шага сборки) на порту 3000, с `reuseExistingServer: !process.env.CI` — чтобы разработчик мог держать dev-сервер запущенным вручную и гонять тесты поверх него локально, но CI поднимал чистый сервер.
- **npm-скрипт:** `"test:e2e": "playwright test"` в `apps/web/package.json`, аналогично `test:e2e` в `apps/api` — план прямо просит именно такое имя скрипта.
- **API-хелпер внутри теста** («файл создать через API-хелпер в тесте», Фаза 3): тест не должен гонять реальный UI формы загрузки (Фаза 4 ещё не реализована на момент Фазы 3) — вместо этого Playwright-тест перед открытием страницы делает прямой HTTP-запрос к `apps/api` (`POST /auth/register` или `/login` для получения токена, `POST /meetings`, затем `POST /meetings/:id/file` с файлом-фикстурой через `multipart/form-data`), используя `request` fixture Playwright (`test.extend`/встроенный `APIRequestContext`), а не `fetch`/`axios` отдельно — Playwright даёт для этого `request.post(url, { multipart: {...} })` без сторонних зависимостей. Это требует, чтобы **`apps/api` был запущен** при прогоне frontend e2e (в отличие от backend e2e-спеков, которые самодостаточны) — стоит явно задокументировать в `apps/web/CLAUDE.md` при реализации Фазы 3: Playwright e2e для `apps/web` требует одновременно поднятых `apps/api` (порт 3001) и БД (`docker compose up -d`), в отличие от `test:e2e` в `apps/api`, который самодостаточен.
- **Тестовый файл-фикстура:** небольшой статичный файл (например, `apps/web/e2e/fixtures/sample.pdf` или `.txt`) закоммиченный в репозиторий — не генерировать на лету, чтобы тест был детерминированным и не зависел от рантайм-генерации бинарных данных.
- **Изоляция данных между тестовыми прогонами:** по аналогии с backend e2e (очистка таблиц в `beforeEach`), но с browser-стороны это недоступно напрямую — вариант: (а) each Playwright test регистрирует нового случайного пользователя (`email: `test-${randomUUID()}@example.com`) через API-хелпер, что даёт естественную изоляцию без необходимости чистить БД между прогонами, либо (б) добавить тестовый API-эндпоинт для очистки — вариант (а) проще и не требует production-кода «только для тестов», рекомендуется.

## 7. Открытые вопросы для уточнения на этапе реализации (не блокируют research, но влияют на Фазу 2)

1. **Кто имеет право читать/скачивать файл встречи** — только организатор, или также перечисленные `participants` (и если да — как связать `participants: String[]` с авторизованным пользователем, которого сейчас в модели нет)? См. §3. Рекомендация: на объём текущего PRD — только организатор, симметрично остальным `/meetings/:id` эндпоинтам.
2. **Замена MIME-валидации** (заявленный `mimetype` vs magic-byte через `file-type`) — стоит решить в Фазе 1, а не откладывать, см. §1.
3. **Кодировка `Content-Disposition` для кириллических имён файлов** — включить в тесты `meeting-file.e2e-spec.ts` явно (файл с русским именем), не полагаться на то, что дефолтная реализация Nest справится сама.
