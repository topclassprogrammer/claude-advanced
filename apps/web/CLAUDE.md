# apps/web

Фронтенд на Next.js 16 (App Router) + React 19 + TypeScript. Компонентная/файловая детализация — см. «Структуру» ниже.

Маршруты:

- `/auth/register`, `/auth/login` (`src/app/auth/{register,login}/page.tsx`) — регистрация и вход, `POST /auth/register`/`POST /auth/login`, страницы ссылаются друг на друга. Поле пароля с переключателем видимости — `PasswordField` (см. «Структуру»). Оба экрана — двухпанельная вёрстка по `design/VideoMeeting.pen` (node `q8oK3` «Auth 1 — Регистрация» и node `xq4Z4` «Auth 2 — Вход», у обоих одинаковая Promo Panel, различается только заголовок-питч): общий `AuthScreenShell` (тёмная промо-панель `AuthPromoPanel` с питчем продукта + белая панель с формой; на узких экранах промо-панель скрыта, вместо неё компактный бренд-хедер над формой). У логина, в отличие от макета, сознательно нет ссылки «Забыли пароль?» — в API нет функциональности восстановления пароля (см. `apps/api/CLAUDE.md`), то же решение принято для email-поля на регистрации.
- `/` и `/meetings/[id]` (`src/app/page.tsx`, `src/app/meetings/[id]/page.tsx`) — требуют авторизации, оба — тонкие обёртки над одним и тем же экраном `MeetingsScreen` (`src/components/meetings/MeetingsScreen.tsx`, см. design/VideoMeeting.pen node `o5xFBj` «App — Встречи»): двухколоночный экран «список встреч + деталь-колонка» в стиле Gmail, а не отдельные страницы списка и деталей. `/` рендерит его без выбранной встречи (только список), `/meetings/[id]` — с встречей, выбранной в деталь-колонке (`initialMeetingId` из `params.id`); выбор строки списка не грузит отдельную страницу, а делает `router.push('/meetings/:id')` — тот же экран, обновляется только деталь-колонка. На узких экранах (`<lg`) сайдбар скрыт, а список и деталь-колонка показываются по очереди (деталь — с кнопкой «Ко всем встречам» в шапке), а не рядом.
  - `AppSidebar` — бренд, «Создать встречу» (`CreateMeetingModal`), навигация («Все встречи» — рабочий пункт; «Записи»/«Транскрипты»/«Задачи»/«Участники» — задизейблены, под ними нет бэкенда), индикатор хранилища (задизейблен — нет API квоты), карточка пользователя (`Avatar`+имя/email, выход).
  - `AppTopbar` — заголовок, поиск/фильтры/уведомления/глобальная загрузка (все задизейблены — нет соответствующих эндпоинтов); на узких экранах дублирует «Создать встречу» (иконкой) и выход, раз сайдбар скрыт.
  - `MeetingListColumn` + `MeetingListCard` — `SegmentedControl` «Прошедшие»/«Предстоящие» (реальные, через `groupMeetings`, `src/lib/meeting-grouping.ts`) и «Черновики» (задизейблен — нет такого статуса встречи), группировка по месяцам, client-side «Показать ещё N» (без бэкенд-пагинации — `GET /meetings` и так возвращает все встречи разом), карточка-подсказка «Подключить календарь» (статична). `MeetingListCard` не показывает длительность/статус транскрипта/тег команды из макета — этих данных нет в `Meeting` без N+1 запроса файлов на каждую строку.
  - `MeetingDetailColumn` (+ `MeetingDetailHeader`, `MeetingDetailTabs`, `MeetingOverviewBody`, `MaterialsSection`) — грузит встречу (`GET /meetings/:id`) и её файлы через `useMeetingFiles` (тот же хук, что и раньше). Бейдж «Обработана» — реальный (есть файл с `summary.status === 'COMPLETED'`), тег категории из макета не показывается (нет такого поля). Кебаб-действие — существующая `DeleteMeetingButton` (перенесена из строки списка в заголовок деталь-колонки; e2e обновлены соответственно — сначала клик по строке, затем удаление). Аудио/видео-плеер (`src/components/ui/AudioPlayer.tsx`) — реальное воспроизведение через `<audio>` и blob-URL (`getMeetingFileObjectUrl`), рендерится только если есть подходящий файл; waveform декоративный. Вкладки «Обзор» (по умолчанию — превью выжимки/транскрипта + карточки «Задачи» (задизейблена) и «Материалы»), «Транскрипт» (полный текст), «Материалы» (`FileCard`+`FileUploadForm`, единственное место на экране, где они рендерятся), «Участники» (список строк `participants`) — реальные; «Задачи» задизейблена. Используют `role="tablist"`/`role="tab"`, а не кнопки — иначе имя пересекается с триггером дисклоужера «Транскрипт» внутри `FileCard`.
- `/profile` (`src/app/profile/page.tsx`) — требует авторизации, см. `design/VideoMeeting.pen` node `snVvB` «App — Профиль». Тот же каркас сайдбар+топбар, что и у `MeetingsScreen` (переиспользует `AppSidebar`; топбар — отдельный `ProfileTopbar`, т.к. на этом экране нет поиска/фильтров/создания встречи из макета, только «На главную»/«Выйти»), и две колонки карточек `SettingsCard` (`src/components/profile/*`, общая карточка с иконкой/заголовком/задизейбленным кебаб-действием в шапке — кебаб оставлен только для визуального соответствия макету, контекстного меню под ним нет): слева `AccountSummaryCard` (аватар/имя/email/роль + показатели «Встреч»/«Записи»/«Хранилище» — «Встреч» реальный, через длину `GET /meetings`, два других задизейблены — нет отдельного понятия записей и квоты хранилища в API), `AccountDataCard` (email/роль реальные, часовой пояс/дата регистрации/последний вход задизейблены — `Profile` не отдаёт эти поля) и `SecurityCard` (2FA/активные сессии/удаление аккаунта — все три задизейблены, нет бэкенда); справа те же формы, что и раньше, каждая в своей `SettingsCard`: `ProfileNameForm` (`PATCH /users/me/name`), `AvatarUpload` (`POST`/`DELETE /users/me/avatar`, с отдельным превью `Avatar` рядом — сама `AvatarUpload` содержит только дропзону и кнопку удаления) и `ChangePasswordForm` (`PATCH /users/me/password`, три поля через `PasswordField` — «Текущий пароль»/«Новый пароль»/«Подтверждение нового пароля»; кнопка отправки задизейблена, пока новый пароль и подтверждение не совпадут; при 401 от неверного текущего пароля показывает сообщение из ответа API).

Защита `/`, `/meetings/[id]` и `/profile` — клиентская: `useSession` при монтировании страницы сначала восстанавливает access-токен в памяти через silent-refresh (`POST /auth/refresh` по httpOnly refresh-куке — она одна переживает перезагрузку страницы), затем загружает текущего пользователя (`GET /auth/me`), и редиректит на `/auth/login` через `next/navigation`, если что-то из этого не удалось; серверного middleware/проверки нет.

Иконка типа файла подбирается по MIME-префиксу в `src/lib/file-icon.tsx` (`getFileIcon`, используется и в `FileCard`, и в `FileUploadForm`): `video/*` → `VideoIcon`, `audio/*` → `AudioIcon`, остальное (документы) → `FileIcon`.

## UI-библиотека

Подключен HeroUI v3 (`@heroui/react`, `@heroui/styles`, `tailwind-variants`) поверх Tailwind CSS v4 (`tailwindcss`, `@tailwindcss/postcss`). Провайдер не требуется (v3 не использует `HeroUIProvider`). Стили подключаются в `src/app/globals.css` через `@import "tailwindcss";` и `@import "@heroui/styles";` (порядок важен — эти импорты должны идти первыми в файле). PostCSS настроен в `postcss.config.mjs`. Компоненты HeroUI — compound-паттерн (`<Card><Card.Header>...`), события — `onPress` вместо `onClick`; страницы/компоненты, использующие обработчики событий, должны быть клиентскими (`"use client"`).

Тема — только светлая. Палитра/типографика/скругления — токены дизайн-системы (`design/VideoMeeting.pen`, node `r52SBt`), перенесённые в `globals.css` путём переопределения переменных темы HeroUI (`--background`, `--foreground`, `--surface`, `--surface-secondary`, `--accent`, `--accent-soft`, `--success`/`-soft`, `--warning`/`-soft`, `--danger`/`-soft`, `--border`, `--border-secondary`, `--default`, `--muted`, `--field-background`/`--field-border`/`--field-radius`) — это официальный механизм кастомизации темы HeroUI (см. `node_modules/@heroui/styles/dist/themes/default/variables.css`), а не обход её системы стилей. Токены без аналога в HeroUI (`text-3`, сайдбар, панели) заведены отдельными переменными (`--text-tertiary`, `--sidebar`, `--sidebar-foreground`, `--panel-secondary`, `--panel-tertiary`). Шкала скруглений дизайн-системы объявлена в `@theme inline` под именами по назначению — `--radius-chip`(6)/`--radius-control`(8)/`--radius-block`(12)/`--radius-card`(16) — намеренно не переиспользует т-shirt-шкалу самого HeroUI (`--radius-xs…--radius-4xl`), чтобы её не сломать. Форма нескольких компонентов HeroUI, зашитая в их собственный класс мимо переопределяемых переменных (`.button` — по умолчанию pill, `.card`/`.chip` — свой `border-radius`), точечно переопределена в `globals.css` под эту шкалу; остальные компоненты HeroUI (Badge, Toast, Avatar и т.д.) не тронуты, так как в проекте не используются. Шрифт — Inter (`next/font/google`, `apps/web/src/app/layout.tsx`) с 9-ступенчатой шкалой типографики (`text-display`…`text-overline` в `@theme inline`). Переопределять `--background`/`--foreground` через `@media (prefers-color-scheme: dark)` по-прежнему нельзя — эти имена совпадают с переменными темы HeroUI, которая переключает палитру по атрибуту `data-theme` (`light`/`dark`), а не по `prefers-color-scheme`. Тёмную тему добавлять только через `next-themes` (`attribute="class"`) по инструкции HeroUI, если/когда она понадобится.

Переиспользуемые компоненты дизайн-системы — `src/components/ui/*.tsx` (атомы: `IconButton`, `Badge`, `Counter`, `StatusDot`, `TimestampChip`, `SegmentedControl`, `InlineStateBanner`; составные блоки под будущие экраны: `MeetingListItem`, `FileRow`, `TaskRow`, `TranscriptLine`, `AudioPlayer`, `NavItem`, `AppShell`) — презентационные, без бизнес-логики и без подключения к текущим маршрутам (интеграция в реальные страницы — отдельная последующая фаза). Живая витрина всех токенов и компонентов — `/design-system` (`src/app/design-system/page.tsx`), без авторизации.

## Обращение к API

Адрес `apps/api` задаётся переменной окружения `NEXT_PUBLIC_API_URL` (см. `.env.example`, локально — `.env.local`, по умолчанию `http://localhost:3001`). Клиенты в `src/lib/*-api.ts` — тонкие обёртки над `fetch`, кидающие `ApiError` с сообщением из ответа API при ошибке (список файлов и эндпоинтов — см. «Структуру»); все обычные запросы идут через `authorizedFetch` (`src/lib/auth-api.ts`) — она сама прикладывает `Authorization: Bearer <accessToken>` и один раз молча обновляет токен при 401. `register`/`login`/`logout`/`refreshAccessToken` вместо этого идут напрямую через `fetch` с `credentials: 'include'` (нужно для приёма/отправки httpOnly refresh-куки — единственное место, где куки участвуют во фронтенд-коде). API должен разрешать CORS для origin'а веб-приложения с `credentials: true` (см. `WEB_ORIGIN` в `apps/api/CLAUDE.md`).

Двухтокенная схема (см. также «Аутентификация» в `apps/api/CLAUDE.md`): короткоживущий access-токен живёт только в переменной модуля `src/lib/auth-api.ts` (не в React state, не в localStorage, не в куке) — теряется при полной перезагрузке страницы. Долгоживущий refresh-токен лежит в httpOnly-куке, которую ставит/чистит/ротирует API (`POST /auth/login`/`register`/`refresh`/`logout`) и которую JS не видит и не трогает напрямую — только `credentials: 'include'` заставляет браузер её отправить/принять.

- `authorizedFetch(path, init)` (`auth-api.ts`) — прикладывает текущий access-токен из памяти; при 401 от API один раз вызывает `dedupedRefresh()` (обёртка над `refreshAccessToken()`/`POST /auth/refresh`, дедуплицирует конкурентные вызовы общим промисом) и повторяет запрос с новым токеном; если и это не помогло — отдаёт исходный 401-ответ вызывающему коду как есть (никакого автоматического редиректа на логин из самого `authorizedFetch` — этим занимается `useSession` на уровне страницы). Используется всеми `*-api.ts`, кроме `meeting-file-api.ts#uploadMeetingFile` (см. ниже).
- `useSession` (`src/hooks/useSession.ts`) — единственный способ узнать текущего пользователя на клиенте: если access-токена в памяти ещё нет (первая загрузка страницы), сначала вызывает `dedupedRefresh()` — не «голый» `refreshAccessToken()`, иначе React Strict Mode в dev (двойной вызов эффекта при монтировании) отправляет два конкурентных `POST /auth/refresh` с одной и той же ещё не ротированной refresh-кукой, и один из них 401-ит: grace period на бэкенде (см. apps/api/CLAUDE.md) покрывает только повторное предъявление уже ротированного токена, а не гонку двух ротаций одного и того же токена; затем `getCurrentUser()` (`GET /auth/me`, тоже через `authorizedFetch`), которая возвращает `{ sub, email }`. Редиректит на `/auth/login` через `next/navigation`, если refresh или `/auth/me` не удались. `logout()` из того же хука вызывает `POST /auth/logout` (очищает refresh-токен и на бэкенде, и в памяти) и затем редиректит.
- Компоненты, которым раньше передавался `token` пропом (`Avatar`, `FileCard`/`FileUploadForm`, `CreateMeetingModal`, `DeleteMeetingButton`, `ProfileNameForm`, `ChangePasswordForm`, `AvatarUpload` и т.д.), его не принимают — авторизация полностью инкапсулирована в `*-api.ts`. Для определения организатора (`FileCard.canDelete`, `MeetingDetailColumn.canDelete`) страницы передают `session.userId` (из `useSession`) вниз явным пропом.
- `meeting-file-api.ts#uploadMeetingFile` — исключение: использует `XMLHttpRequest` напрямую (нужны события прогресса, `authorizedFetch` этого не даёт), поэтому сам прикладывает `Authorization` через `getAccessToken()` (`auth-api.ts`) и не умеет молча обновлять токен при 401 в середине загрузки — в этом редком случае пользователь просто увидит ошибку загрузки и должен будет обновить страницу/повторить попытку.

## Команды (запускать из этой директории или через `--workspace=web` из корня)

Скрипты — см. `package.json`. `test:e2e` (Playwright, конфиг `playwright.config.ts`, тесты в `e2e/`) сам поднимает `next dev` (см. `webServer` в конфиге), но требует запущенных `apps/api` и PostgreSQL (`docker compose up -d` из корня) — тесты обращаются к реальному API через хелперы в `e2e/helpers/api.ts` (регистрация пользователя, создание встречи, загрузка файла напрямую через `fetch`, в обход UI).

Любое изменение UI (новая страница, компонент, стили, вёрстка) считается завершённым только после того, как оно:

1. Визуально протестировано в браузере (запустить `next dev` и открыть страницу через Playwright MCP — см. правило использования Playwright MCP для визуальных проверок), а не оценено только по коду. Проверять основной сценарий и граничные случаи (валидация, ошибки, пустые/длинные значения и т.д.).
2. Проверено по скиллу `ui-ux-pro-max` (вызвать явно, не полагаться на память о нём).

Пропускать эти шаги нельзя, даже если изменение выглядит небольшим — вёрстка HeroUI/Tailwind в этом проекте уже ломалась незаметно по коду и обнаруживалась только визуально.
